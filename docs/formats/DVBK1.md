# DVBK1 version 1

The `.dvmbak` file is an uncompressed POSIX-style tar stream. Every entry is a regular file. Entry names use `/` and are exactly `public-format.json`, `vault.header`, `metadata.db.snapshot`, `manifest.enc`, or `blobs/<lowercase-hyphenated-UUID>.dvb`. No directories, links, device entries, PAX extensions, absolute paths, alternate separators, duplicate names, or additional members are accepted. The archive ends with tar zero blocks. The verifier caps entries at 100,003 and rejects trailing nonzero data. It copies members in 64 KiB chunks to a private verification directory; the archive, DB, and blobs are never held whole in memory.

`public-format.json` is UTF-8 JSON with exactly `magic: "DVBK1"`, `format_version: 1`, a UUID `backup_id`, `manifest_algorithm: "HKDF-SHA-256+XChaCha20-Poly1305"`, and `manifest_version: 1`. It has no source paths, item names, credentials, or keys. The exact serialized bytes, including their ordering and whitespace, are the manifest AEAD associated data.

`manifest.enc` is `DVBK1M1\0` (8 bytes), a fresh 24-byte XChaCha20 nonce, then ciphertext and its 16-byte Poly1305 tag. HKDF-SHA-256 uses the G2 VMK-derived BackupKey as input key material, UTF-8 `backup_id` as salt, and ASCII `DVM/DVBK1/manifest/v1` as info to derive 32 bytes. It does not change the root BackupKey derivation. The encrypted JSON has `backup_id`, `vault_id`, `format_version`, `app_version`, `schema_version`, `created_at_unix_seconds`, `members`, `canonical_blob_count`, and `canonical_logical_bytes`. Each member record contains its logical path, stored-byte size, and lowercase hex SHA-256. The manifest lists all members except itself. Its size is capped at 16 MiB; the public format at 4 KiB and header at 16 KiB.

`metadata.db.snapshot` is a keyed SQLCipher Online Backup API snapshot. `vault.header` is the G2 header. Blobs are unchanged encrypted DVB1 files. The referenced blob set is enumerated from the snapshot's `item_blobs` join, not a later live query. Derived indexes, logs, locks, temporary files, quarantine, and OS credential-store entries are absent.

STRUCTURAL verification checks tar structure and names, header parse and credential unlock, manifest authentication, all stored-byte sizes and hashes, SQLCipher and SQLite integrity, migration history, and equality of the manifest and snapshot blob sets/counts/totals. FULL additionally decrypts every referenced DVB1 blob through a discard sink and compares its plaintext SHA-256 and size with the encrypted DB. Only a completed FULL result may be called restorable. Unknown format or migration versions fail closed.
