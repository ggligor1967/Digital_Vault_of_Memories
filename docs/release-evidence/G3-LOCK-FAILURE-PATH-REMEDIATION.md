## Lock acquisition inventory and root cause

All repository `try_lock()` acquisitions are in `dvm-storage`. `owner.lock` and `keyslots.lock` are otherwise opened for creation or inspected as data, without acquiring their advisory locks.

| Path                                            | Old acquisition                                                                                                                  | Old early-return behavior                                                                                           | New owner                                                       |
| ----------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| `ProtectedVault::unlock`, `keyslots.lock`       | Raw `File::try_lock()`, then header parsing, slot selection, authentication, and vault open; `FileLockOwner` only in `OpenVault` | The raw `File` could leave scope before explicit `unlock()`; a duplicated or inherited handle could retain the lock | `FileLockOwner::try_acquire` immediately after opening the file |
| `Vault::create_with_injected_key`, `owner.lock` | Raw `File::try_lock()`, then header write, key derivation, database open, and canonicalization; owner only in returned `Vault`   | Same gap on any later failure                                                                                       | `FileLockOwner::try_acquire` immediately after opening the file |
| `Vault::open_with_injected_key`, `owner.lock`   | Raw `File::try_lock()`, then key derivation and database open; owner only in returned `Vault`                                    | Same gap on any later failure                                                                                       | `FileLockOwner::try_acquire` immediately after opening the file |

Classification: **A — EARLY_RETURN_LOCK_GUARD_GAP**. The prior R2 duplicated-handle tests exercised successful-owner `Drop`; they did not return an error between `try_lock()` and owner construction. The new helper retains the old `VaultLocked` mapping on lock-acquisition failure, constructs the explicit-unlock owner immediately on success, and leaves credential selection and error classification unchanged. The captured duplicate is a thread-local test seam; it is absent from production builds.

The old published head passed the exact isolated Ubuntu test 100/100 times and the full storage lib suite twice with normal test parallelism. This does not erase the published CI failure or make it transient. It shows that the inherited-handle condition needs a deterministic oracle.

## Deterministic lock oracles

- A recovery-declined vault has neither recovery nor device slot. One test repeats `Recovery → BadPassphrase` followed immediately by `Device → ProviderUnavailable` 100 times and checks unchanged durable bytes and no credential creation.
- A thread-local seam duplicates the keyslot lock immediately after acquisition. After missing-recovery failure, the duplicate remains live while the missing-device attempt acquires independently and returns `ProviderUnavailable`.
- A thread-local fault after `owner.lock` acquisition forces `Vault::open_with_injected_key` to return `Internal`. The duplicate remains live while another vault owner opens successfully.
- Existing live-owner tests prove that a second keyslot or vault owner gets `VaultLocked` while the first is live, and can open after the first drops.
- Negative control, isolated Ubuntu copy: restored the old delayed keyslot owner construction while keeping duplicate capture immediately after raw `try_lock()`. The new oracle failed exactly with `left: VaultLocked`, `right: ProviderUnavailable`. Restored the immediate-guard source bytes, compared them to the workspace files, and reran the oracle successfully. No negative-control mutation is in the repository.
