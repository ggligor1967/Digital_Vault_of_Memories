## R2: G0 lock lifetime

- Classification: **PRODUCTION_LOCK_LIFETIME_DEFECT**. The two G2 advisory owner handles were released only by closing `File`. Rust documents that a lock can remain held while a duplicated or inherited descriptor remains open, and that `File::unlock` releases it explicitly. [Rust File locking](https://doc.rust-lang.org/std/fs/struct.File.html).
- Exact published head in WSL Ubuntu, isolated header matrix with one test thread: 10/10 PASS. Normal-parallelism storage suite: first pass 47 passed, one ignored; second pass failed with `VaultLocked` in `device_enrollment_retains_the_credential_it_activated`. Further diagnostic normal-parallelism runs reproduced `VaultLocked` in the device matrix and a G1 owner-reopen test. Failure localization identified `before-activation` credential paths and `TryLockError::WouldBlock`, rather than an I/O error.
- Test-only Linux lock snapshots calibrated intentional same-process contention at two open descriptors. A reproduced unexpected `WouldBlock` had only the attempted descriptor open and no persistent `/proc/locks` record by the time diagnostics ran. This is consistent with a short-lived inherited descriptor; the deterministic duplicate-handle regression below proves the lifetime mechanism directly.
- Two deterministic regressions duplicate the owner and keyslot file handles, assert the single-owner refusal while the owner lives, drop the owner, and require a successor to unlock while the duplicate remains. Against the old production code both tests failed with `VaultLocked`; against the correction both passed. These tests are the R2 negative control and preserve live-owner exclusivity.
- A `FileLockOwner` guard explicitly unlocks when its owning field drops. The vault's database field precedes its owner guard, so database destruction completes before unlock; Rust guarantees struct-field drop order. The keyslot guard likewise remains last in `OpenVault`. [Rust destructor order](https://doc.rust-lang.org/reference/destructors.html).
- Post-fix Linux isolated header matrix: 50/50 consecutive PASS, one test thread. Complete `cargo test --workspace --locked --quiet` with normal parallelism: 3/3 complete PASS. A fourth optional run was stopped and is not counted. Focused stress: 100/100 header-matrix executions across four concurrent Linux test processes PASS, zero failed results. The first full workspace attempt was blocked at build by missing WSL WebKit development libraries; the same Ubuntu CI WebKit prerequisites were installed before the three complete passes.
